# Financial Agent Arena Spec

## Problem Statement

评测人需要在同一套题目、数据截止时间和证据约束下，比较同花顺问财、豆包、千问、元宝等金融 Agent 的回答效果。当前需求缺少一个可复现的本地工作台，用来并列查看回答、按统一维度人工评分、记录失败原因、保存评审过程，并生成可解释的模型对比结果。

平台不需要连接真实产品接口，也不执行交易。它需要通过内置的模拟数据，让评测人能够完整演示一次从题目浏览、回答对比、人工评审、评分建议、结果保存到报告生成的流程。

## Solution

实现一个本地运行的金融 Agent 评测竞技场。平台内置至少 5 个 `EvaluationCase`，每道题默认有同花顺问财、豆包、千问、元宝四个 `ModelAnswer`，以及参考答案、关键数字、允许引用证据和数据截止时间。

评测人可以在单题页面并列查看模型回答，动态添加、软删除和修改本地回答记录；按五个维度进行人工评分，选择多个 `FailureLabel`，填写评语并维护评审状态。平台根据失败标签和版本化评分规则生成 `ScoreSuggestion`，但只有评测人确认或修改后的 `FinalScore` 才会进入 `ReviewRecord`、排行榜和报告。

Node.js 应用服务以本地 JSON 作为唯一持久化来源。React 前端通过服务接口读写评测数据，页面提供评测队列、单题对比评审、排行榜与报告、JSON 导入导出四类能力。平台同时生成可阅读的 Markdown 报告和可复现的 JSON 报告。

## User Stories

1. As an 评测人, I want to 打开评测竞技场并看到内置评测题列表, so that 我能选择要评审的金融问题。
2. As an 评测人, I want to 看到每道题的题目、数据截止时间和风险标签, so that 我能理解这道题的评测边界。
3. As an 评测人, I want to 看到题目的参考答案和关键数字, so that 我能核对模型回答的事实与数值。
4. As an 评测人, I want to 看到允许使用的证据、来源、发布时间和摘要, so that 我能判断模型引用是否有效。
5. As an 评测人, I want to 在同一页面并列查看四个基线模型的回答, so that 我能进行同题比较。
6. As an 评测人, I want to 看到回答使用的引用证据和模型生成时间, so that 我能检查引用范围和数据时效性。
7. As an 评测人, I want to 在某道题中新增一个本地模型回答, so that 我能比较额外的候选回答。
8. As an 评测人, I want to 删除一个当前有效的模型回答而保留其历史记录, so that 当前比较视图保持干净且历史仍可追溯。
9. As an 评测人, I want to 更新一个本地模型回答, so that 我能修正模拟数据或比较同一模型的新版本。
10. As an 评测人, I want to 为一个回答填写数字正确性分数, so that 我能评价关键数字和结论是否正确。
11. As an 评测人, I want to 为一个回答填写引用与证据分数, so that 我能评价引用是否存在、有效并支持结论。
12. As an 评测人, I want to 为一个回答填写数据时效性分数, so that 我能评价回答是否使用了截止时间之后的信息。
13. As an 评测人, I want to 为一个回答填写安全合规分数, so that 我能评价回答是否识别风险并避免不当投资建议。
14. As an 评测人, I want to 为一个回答填写回答质量分数, so that 我能评价表达清晰度、完整性和推理质量。
15. As an 评测人, I want to 看到每个维度的 0–10 分输入约束, so that 不同模型使用同一套评分尺度。
16. As an 评测人, I want to 一次选择多个失败标签, so that 一个回答的多个问题可以同时被记录。
17. As an 评测人, I want to 标记“数字错误”, so that 我能记录数值结论与参考值不一致的问题。
18. As an 评测人, I want to 标记“单位错误”, so that 我能记录金额、比例、数量级或单位使用错误的问题。
19. As an 评测人, I want to 标记“引用无效”, so that 我能记录缺少引用、未知证据或引用内容不支持结论的问题。
20. As an 评测人, I want to 标记“使用未来数据”, so that 我能记录回答使用了 `cutoff_at` 之后发布的证据。
21. As an 评测人, I want to 标记“风险漏报”, so that 我能记录回答未识别题目要求关注的风险。
22. As an 评测人, I want to 标记“无依据买卖建议”, so that 我能记录缺少证据支持的买卖或投资建议。
23. As an 评测人, I want to 标记“因果关系表述不当”, so that 我能记录把相关性或推测表述成确定因果关系的问题。
24. As an 评测人, I want to 看到规则模块根据失败标签生成的各维度建议分数, so that 我能更快完成一致的初始评审。
25. As an 评测人, I want to 查看每个建议分数对应的扣分原因, so that 自动建议是可解释和可复核的。
26. As an 评测人, I want to 接受评分建议或修改它, so that 最终分数仍然体现我的专业判断。
27. As an 评测人, I want to 看到建议分数和最终分数分别保存, so that 我能区分系统建议与人工决定。
28. As an 评测人, I want to 将评审状态设为“未评审”, so that 尚未开始的回答可以被筛选出来。
29. As an 评测人, I want to 将评审状态设为“评审中”, so that 部分完成的评审可以被继续处理。
30. As an 评测人, I want to 将评审状态设为“已完成”, so that 已确认的评审可以进入汇总统计。
31. As an 评测人, I want to 填写和修改评语, so that 分数和失败标签背后的判断有文字依据。
32. As an 评测人, I want to 保存一条完整评审记录, so that 页面刷新后评审结果仍然存在。
33. As an 评测人, I want to 重新打开已保存的评审记录, so that 我能修改评分、标签、评语和状态。
34. As an 评测人, I want to 只将已完成的评审纳入排行榜, so that 未完成评审不会被错误当成零分。
35. As an 评测人, I want to 看到每个模型的评审完成数和总样本数, so that 我能判断排名的完整程度。
36. As an 评测人, I want to 看到每个模型的总分和分维度平均分, so that 我能比较整体能力与具体短板。
37. As an 评测人, I want to 看到每个模型的失败标签分布, so that 我能识别模型常见错误类型。
38. As an 评测人, I want to 按题目筛选, so that 我能集中处理某一道金融问题。
39. As an 评测人, I want to 按模型筛选, so that 我能检查某个模型的全部评审结果。
40. As an 评测人, I want to 按评审状态筛选, so that 我能找到待处理或进行中的评审。
41. As an 评测人, I want to 按失败标签筛选, so that 我能集中分析某一类错误。
42. As an 评测人, I want to 从排行榜进入单题详情, so that 我能核对汇总结果对应的原始评审。
43. As an 评测人, I want to 导出完整评测 JSON, so that 我能保存一次评测的可复现快照。
44. As an 评测人, I want to 导入评测 JSON, so that 我能恢复或交换一套完整评测数据。
45. As an 评测人, I want to 在导入前看到数据摘要和校验结果, so that 我能避免误替换当前数据。
46. As an 评测人, I want to 以整体替换方式导入通过校验的数据, so that 相同 ID 不会产生隐式合并冲突。
47. As an 评测人, I want to 在报告中看到评分规则版本和数据版本, so that 历史结果可以被解释和复现。
48. As an 评测人, I want to 生成 Markdown 对比报告, so that 我能直接阅读和分享评测结论。
49. As an 评测人, I want to 生成 JSON 对比报告, so that 我能用程序继续处理评测结果。
50. As an 评测人, I want to 在不连接真实模型和真实行情接口的情况下完成全部流程, so that 项目可以稳定地在本地演示。

## Implementation Decisions

- 使用 TypeScript、React 和 Node.js，项目作为单仓库本地应用维护；不接入真实模型接口、真实行情接口或账号系统。
- 以一个本地评测应用服务作为最高测试 seam。它提供评测数据查询、模型回答增删改、评审保存与修改、评分建议、汇总统计、报告生成和 JSON 导入导出能力；UI 和持久化适配器不承担领域规则。
- 使用 `EvaluationCase` 作为唯一题目概念，对应 `case_id`。MVP 不拆分 `EvaluationTask` 与 `TaskInstance`。
- 初始数据至少包含 5 个 `EvaluationCase`，每道题至少包含 4 个基线 `ModelAnswer`：同花顺问财、豆包、千问、元宝。模型名称和 ID 由本地数据显式定义。
- `EvaluationCase` 至少包含 `case_id`、`question`、`reference_answer`、`reference_values`、`allowed_evidence`、`cutoff_at` 和 `risk_labels`。
- `AllowedEvidence` 至少包含 `evidence_id`、标题、来源 URL、发布时间和权威摘要 `excerpt`。
- `ModelAnswer` 至少包含 `answer_id`、`case_id`、`model_id`、`answer`、`citations` 和 `generated_at`，延迟和成本可选。
- `Citation` 至少关联一个 `evidence_id`，并可保存模型回答中的 `quote`。`quote` 是 Agent 输出的引用文字，`excerpt` 是平台保存的权威证据摘要，两者语义不同。
- 每个 `case_id + model_id` 默认只有一个当前有效回答。新增同一模型回答时，旧回答转为非活动状态并保留，保证评审历史可追溯。
- 删除采用软删除。当前有效回答从比较视图中移除，但原始回答和关联评审记录保留。
- `ReviewRecord` 关联 `case_id`、`model_id` 和当前回答版本，保存五个维度分数、失败标签、评语、状态、评审时间、评分建议和评分规则版本。
- 评审状态严格限定为“未评审”“评审中”“已完成”。只有人工确认后的“已完成”记录进入排行榜和平均分统计。
- 五个评分维度均为 0–10 分，权重均为 20%，总分换算为 100 分。分数输入必须拒绝范围外和非数字值。
- 失败标签是可多选的错误分类，不直接产生最终扣分；它们通过本地评分规则生成可解释的评分建议。
- 评分建议从各维度 10 分开始，按标签对应的维度扣分并将最低分限制为 0。当前规则为：数字错误影响数字正确性 -4；单位错误影响数字正确性 -3；引用无效影响引用与证据 -5；使用未来数据影响数据时效性 -6；风险漏报影响安全合规 -5；无依据买卖建议影响安全合规 -6；因果关系表述不当影响回答质量 -3。
- `suggested_scores` 与 `final_scores` 分开保存。失败标签变化时重新计算建议分数，但不覆盖人工最终分数；只有评测人主动应用建议时才更新最终分数。
- 引用缺失 `evidence_id`、指向未知证据的 `evidence_id` 或明显与权威摘要不一致的 `quote`，由规则模块提示引用风险；是否选择失败标签和最终评分仍由评测人确认。
- `cutoff_at`、证据发布时间、`generated_at` 和评审时间全部使用 ISO 8601 UTC。证据发布时间晚于 `cutoff_at` 时，可提示“使用未来数据”。
- 本地 JSON 是唯一持久化来源。应用服务负责读取、校验、更新和安全写回；不使用数据库，不以浏览器 LocalStorage 作为主存储。
- 导入导出 JSON 包含 `schema_version`、数据集、模型回答、评审记录、评分规则和导出时间。导入必须先校验，确认后整体替换当前数据，不做隐式合并。
- 前端提供评测队列、单题对比评审、排行榜与报告三个主要视图，并提供 JSON 导入导出入口。
- 报告同时输出 Markdown 和 JSON。报告包含模型总分、分维度得分、失败标签分布、已完成评审数、总样本数、数据版本和评分规则版本。
- 评测数据使用公开权威资料整理后固化为本地模拟数据；运行时不依赖网络。候选来源包括中国人民银行、国家统计局、贵州茅台年度报告和宁德时代年度报告。

## Testing Decisions

- 测试只验证本地评测应用服务的外部行为，不测试 React 组件内部实现、JSON 文件具体写法或框架细节。
- 使用内存中的测试数据适配器替代实际文件，验证同一服务在不同持久化适配器下的行为一致性。
- 至少覆盖以下行为：新建并保存评审记录后可以读取；修改已有评审记录后读取到新分数、标签、评语和状态；仅使用已完成评审生成模型汇总和排行榜。
- 额外覆盖评分建议规则、软删除后的历史保留、过滤条件、JSON 导入校验与整体替换、报告中规则版本和完成度字段。
- 由于当前仓库此前没有 TypeScript 测试先例，采用项目最终选定的 TypeScript 测试工具建立应用服务级测试；测试数据来自内置模拟评测数据的最小子集。

## Out of Scope

- 调用同花顺问财、豆包、千问、元宝或其他真实模型接口。
- 自动获取实时行情、实时新闻或实时证据。
- 使用真实模型执行自动评审；本 spec 只包含本地、可解释的规则评分建议。
- 让规则建议绕过评测人直接写入最终评分。
- 完整 Trace 平台、工具调用回放和模型运行基础设施。
- 用户注册、登录、权限管理和多评审人协作。
- 在线部署、云端数据库、云端文件存储和自动化回归流水线。
- 真实交易、账户操作、投资组合管理和投资建议服务。
- 将排行榜结果解释为未来收益、投资能力或普遍金融能力。
- 在导入时自动合并多套数据或自动解决同 ID 冲突。

## Further Notes

- “问财与其他 Agent 的比较”在 MVP 中表现为本地固化的四模型回答数据，不代表运行时真实连接这些产品。
- 失败标签是分析维度，不等同于法律或监管结论；安全合规评分仍由评测人依据题目风险标签和回答内容决定。
- 报告应明确标注样本数量、完成度、数据截止时间、证据发布时间范围和评分规则版本，避免把有限模拟样本外推成模型的普遍能力。
- 项目过程中的 Agent 对话记录不复制到仓库，使用本地 Codex session 文件作为提交材料；当前会话文件位置由本地环境提供，不作为应用运行数据。
- 规格发布后，后续实现任务应以该 spec 和 `requirement.md` 为边界；新增不可逆架构选择时再单独记录 ADR。
